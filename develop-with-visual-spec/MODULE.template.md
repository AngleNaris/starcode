## 已批准的设计基线

实施确认前必须用真实产物填写；不能用占位符通过：
- G1 逻辑修订、范围及批准记录 ID：待批准
- G2 图片 ID/修订、实际文件或稳定链接、页面/状态/目标视口：待生成并批准
- 精确文案、token、组件、响应式、长内容与无障碍规则及修订：待填写
- 没画出的状态沿用哪些已批准组件/规则：待填写
- 固定样例 ID、内容位置、角色、字体、主题、截图条件：待填写
- 接受的设计例外及批准记录 ID：待填写；没有时写“无”

## 验收与证据设计

将实际条目同步进原 requirements；以下是文字模板，不是 CLI JSON。按真实需求保留/扩展，每项明确“给定 → 操作 → 结果”、数据模式、验收方法和实际观察面。验收 ID 与原 requirements 对齐，不制造重复条目。

- VIS-1：实现画面对照指定批准图；目标视口、样例、关键结构与允许差异：待填写。方法/观察面：待确定。
- FLOW-1：完整旅程和本次必要的失败/恢复路径：待填写。方法/观察面：待确定。
- DATA-1：真实数据读写、重新读取及相应身份/权限：待填写。方法/观察面：待确定；若范围仅为 mock，明确限制，不标真实集成通过。
- ENG-1：适用构建、类型检查及相关测试：待填写。方法/观察面：待确定。

四类分别需要证据，不能相互代替。纯后台无视觉影响时 VIS/G2 可不适用并说明；图像生成批准不是 VIS 的实现验证。
