# 示例：一段审片流程怎样算做完

以下是虚构示例，展示规格写法，不代表所有影视项目的正确模型。mancode 模式可将本次切片写入 docs/media-review.md 的模块计划；下文 G1/G2 是流程关卡，G3 证据沿用原账本，不建立第二个任务状态。真实项目应从使用者、现有数据和协作方式推导需求。这里没有实际生成图片、运行测试或获得批准。

## 场景与本次范围

导演打开某个剪辑版本，在时间点留下意见，剪辑师处理意见，导演回来确认。

假设本项目把“作品”和“剪辑版本”分开；每条意见属于某个版本，可关联时间点。一个作品可有多个版本。这是本例需要确认的设计选择，不应推广为所有媒体应用的默认结构。

本次包含：版本切换、带时间点的意见、处理状态、刷新后仍可查看。

本次不包含：自动迁移意见到新版本、跨组织权限配置、在线转码。

## AI 应先提出的关键问题

“本例建议意见固定归属其创建时的版本，切换版本时只显示该版本意见。是否需要跨版本保留或映射意见？这会改变数据模型和用户看到的上下文。”

这比先询问卡片圆角更重要。若尚不清楚，先标为 G1 待决项；不能为了快速跑通页面，把所有意见塞进同一个作品级列表。

## G1 逻辑与验收条目

- A1 版本隔离：给定作品有 V1、V2，V1 有一条意见；切到 V2 时，不应将 V1 意见误显示为 V2 意见。当前版本在播放器与意见区都清晰可见。
- A2 时间点意见：给定用户正在看 V2；在指定时间点提交意见后，列表显示准确版本与时间点；点击时间点能定位对应媒体。具体时间码格式按本项目帧率/媒体规则另行确定，不由样式推断。
- A3 保存可靠：意见提交成功后刷新并重新读取，意见仍存在；网络失败时保留输入并显示可重试状态，不显示假成功。
- A4 处理与确认：本例假设剪辑师标记“已处理”，导演才能确认“已通过”。权限与状态转换需获批，再分别用相应角色验证。
- A5 边界：暂无意见时有明确空状态；长中文意见和长版本名不遮挡关键操作；窄屏仍能识别当前版本与提交状态。

这里“带时间点”不自动包含逐帧精度承诺；如果实际审片要求逐帧，应在 G1 写清媒体、帧率、时间码与验收方法。

## G2 要生成和批准什么

候选画面：
- 桌面审片主屏：V2、播放器、版本选择、意见列表、输入区，使用固定样例 F1。
- 意见提交失败状态：显示原输入和重试；如果沿用已批准错误组件，可用主屏加明确组件/行为规则覆盖。
- 窄屏审片主屏：展示播放器与意见区如何重排，不能只把桌面整图缩小。

固定样例 F1 由 AI 准备合成内容，包含两个版本、一条较长中文意见、多条不同状态意见以及长版本名；记录准确文本、角色和时间点。生成图与实现截图都使用这份目标内容。

本例只说明需要的图片与样例，未附任何图片，因此 G2 尚未完成。正式项目必须真实生成、查看并批准后才能实现该切片。

## 为什么测试通过仍可能没完成

单元测试能证明“添加一条评论函数返回成功”，却不能证明它属于正确版本，或刷新后仍存在。

完整旅程应实际执行：打开 V2 → 播放并定位 → 提交意见 → 刷新 → 用另一角色处理 → 返回确认。记录对应验收 ID、数据模式、结果和证据，再独立检查实际 UI 截图是否符合批准图。

若所有操作只连接内存 mock，结论只能是“mock 旅程通过”；真实数据读写未验证。不能因为截图漂亮、构建成功，就标记整个审片工具完成。

## 中途出现新需求时

“希望把 V1 的意见映射到 V2。”

这是数据关系与用户旅程变更，应重开相关 G1 条目，确认映射方式和失效情况；新增视觉交互才重开关联 G2。已批准且不受影响的播放器样式和布局可以保留。

“提交按钮颜色没有按批准图做。”

这是恢复批准外观的小修复：引用原图/token，修复、截图复核、检查相关共享按钮；无需让用户重选整套风格。
