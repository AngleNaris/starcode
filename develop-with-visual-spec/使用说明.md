# 开始使用（v1.1，含 mancode 适配）

这是一套可携带的开发约定：先定交互逻辑，再真实生成 UI 效果图并确认，最后按图实现。本 fork 已收录完整八文件目录，通过 README 与 AGENTS.md 非托管区域提供读取入口，并纳入 npm 打包清单；没有安装到用户全局工具或其他项目。

## 已在用 mancode：直接这样说

把整个 develop-with-visual-spec 文件夹交给开发助手，再发：

> 请在现有 mancode 流程上使用这份 v1.1 视觉开发约定。先读取 MANCODE.md 与 SPEC.md，核对本地版本、宿主入口、原 TaskRef 与 policy。任务与验收仍以 mancode 为准，只用一份绑定模块计划，不再创建 PROJECT.md 状态。先整理交互逻辑、数据关系与完整旅程给我确认；保持最终实施计划待确认，再用真正的图像生成工具生成并展示 UI 效果图。图和补充规则批准后，纳入最终基线，再确认执行。先报告现状、关卡和下一步，不直接写 UI，不修改托管 skill 或托管规则区。

已有 TaskRef 继续原任务；没有时，先确认当前环境支持的入口，不凭本包自动安装或升级。固定源码版本和本地兼容性边界见 [MANCODE.md](MANCODE.md)。你无需填写模板，AI 负责整理，你决定流程、效果图与最终执行范围。

## 没有 mancode：独立使用

> 请按这个文件夹中的 SPEC.md 开展本项目。先读取已有资料，整理本次完整用户流程、核心数据关系和验收范围；列出假设，只问我会改变方案的关键问题。我确认交互逻辑后，再调用真正的图像生成工具生成 UI 效果图给我确认。只有批准的图和对应规则才能进入真实 UI 开发。先报告目前所在关卡和下一步，不直接写界面。

此时复用已有当前入口，必要时再采用 [PROJECT.template.md](PROJECT.template.md)。不要为了使用本包另造文档体系。多轮迭代只审阅改变的部分。

## 八个文件各做什么

- [SKILL.md](SKILL.md)：技能入口，先路由 mancode 或通用模式。
- [SPEC.md](SPEC.md)：完整的阶段、验收与变更约定。
- [PROJECT.template.md](PROJECT.template.md)：仅供无 mancode 的通用项目使用。
- [IMAGE-TO-UI.md](IMAGE-TO-UI.md)：真生图、批准、视觉依据与实装截图复核。
- [EXAMPLE-media-review.md](EXAMPLE-media-review.md)：虚构审片例子，解释完整旅程与数据边界。
- [MANCODE.md](MANCODE.md)：mancode 接入、状态归属、最终计划确认和原账本映射。
- [MODULE.template.md](MODULE.template.md)：mancode 的单份模块计划，使用已核实的四个区块标记。
- 本文件：使用入口与日常提示。

## 在 Codex、DSH 或其他工具中使用

先作为普通文件使用，让助手读取文件夹即可；不要求安装才能理解流程。本 fork 使用显式文件引用，不依赖宿主自动发现；技能名称保持 develop-with-visual-spec。支持技能的宿主可识别 SKILL.md 的 name/description，但自动发现和安装目录取决于实际产品与版本，应先核实，再在你授权后接入。没有验证真实宿主的技能菜单发现，也没有向 Codex 或 DSH 安装全局文件。

mancode 的生成入口仍由 mancode 管理。不要把这份 SKILL.md 覆盖到生成的 man skill，也不要改其托管区。仅在希望长期采用时，确认现有规则后合并非托管引用片段；mancode 使用 [MANCODE.md](MANCODE.md) 的片段。

通用模式可在经授权的项目规则中加入：

```markdown
本项目的 UI 功能开发遵循 ./develop-with-visual-spec/SPEC.md。
先读取本项目已指定的当前入口、批准产物与阻塞。
交互逻辑批准后，使用真实图像生成工具生成并批准 UI 效果图，再实现真实界面。
新需求只重开受影响关卡；恢复已批准规格的小修复使用快速路径。
```

本 fork 的目录位于项目根目录，AGENTS.md 非托管区域已引用它；复制到其他项目时必须重新核验路径，并按授权接入。`mancode init` 不会自动复制本独立目录。规则文件和技能只约束助手流程，不等于运行时能拦截任意提前写代码的动作。

没有真图像生成能力时，停在 G2 并交出提示词、参考与覆盖清单；将生成任务移交有能力的工具，带回真实图片、查看并批准后继续。HTML 或已有代码截图不能替代此关卡。

## 日常继续、变更与小修复

继续开发：
> 读取当前入口、原任务记录和批准图片，从对应关卡继续。先核实引用可访问；完成后更新实际证据。mancode 模式用原 CLI 与账本，不复制通过状态。

想到新需求：
> 我想增加……。先说它影响哪些流程、图片和数据，以及代价；我决定范围后，只重开受影响部分。

修一个偏差：
> 这里与已批准的……不一致。若只是恢复原设计，按小修复路径处理；若必须改变设计，先说明影响。

验收分别看 VIS（视觉）、FLOW（旅程）、DATA（真实集成）、ENG（工程）证据：页面按图做出来、工作确实走通、真实数据有效、检查实际执行。任何一类通过都不自动证明另一类通过。
