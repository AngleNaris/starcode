# 视觉依据：沿用、探索与实装检查

G2 确认本次采用什么视觉依据、改变什么以及哪些决定尚未解决。文件名保留以兼容已有引用；本节不是所有 UI 任务的强制生图入口。mancode 模式的当前入口指绑定模块计划，最终执行确认和账本仍按 [MANCODE.md](MANCODE.md) 处理。

## 1. 先选视觉路由

**inherit 是已有项目的默认路线。** 继续开发、同体系增加页面或布局、添加状态、调整间距和字号，先读取正在使用的系统。找出颜色/字体/间距 token、组件及变体、相邻页面、导航与内容密度、已采用的设计材料和实际运行截图。说明本次复用的规则、局部变化和适用范围，然后在现有授权内实施，不要求新的生成图。

代码与页面是可核对的现状证据，不能据此声称用户过去批准过某张图片。检查来源是否仍有效，并区分稳定设计规则与已知缺陷、临时样式或废弃实现。用户最新要求覆盖其明确改变的部分，余下视觉语言继续保持。

**explore 只用于新的视觉方向。** 新建视觉体系、整体重做或用户明确请求探索新方向时，先确定需要决定什么，再选择真实生图、可运行原型或明确设计规格。可以比较构图、密度、排版等关键差异；不必为每个页面或状态重新选风格。沿用中的体系即使出现新布局，也不自动进入 explore。

**单项资产独立处理。** 用户需要照片、插画、纹理等时，可在 inherit 或 explore 中生成该资产；先约定其用途、大小与已有风格。资产变化不等于 UI 方向变化，不替换周围 token、导航或组件。

## 2. 为本次依据准备内容

从本次逻辑与项目中提取：

- 用户、页面/状态、主要操作和必要信息；真实内容的长度与密度。
- 支持的目标窗口、输入方式、主题、字体与所复用组件。
- 固定样例与观察条件，以便实现前后或与所选产物比较。
- 当前授权覆盖的变化，以及仍会实质改变方向或范围的未决项。

长列表、长中文标题、空数据等样例应有代表性，不以整齐短标题掩盖实际问题。继承项目时优先使用已有 fixture 或合适的脱敏/合成内容；无需为一次小改动重建整套样例与设计文档。

已有截图必须实际查看像素，代码/组件必须实际检查。没有截图时不能假称已完成视觉核验，可先检查代码和现有设计材料，继续独立工作，并在真实 UI 验证阶段补足。

## 3. explore 中选择生图时

以下要求只约束已选择的生图工作；它们不作用于 inherit 或原型路线。

1. 确认实际工具可用，按工具要求调用，先做能解决关键方向问题的画面。
2. 实际查看输出，检查构图、层级、阅读密度、内容覆盖与动作是否容易找到。
3. 把需要用户选择或确认的方向变化集中呈现；已选定方向的衍生页面沿用规则，不重复启动方向审批。
4. 记录真实工具、提示词、参考材料、输出文件/链接、修订、尺寸与适用范围。只有实际生成并查看后才写“已生成并检查”；批准另记真实来源。

### 可直接使用的提示词骨架

> 为以下已明确的交互方案生成可审阅的 UI 方向图。
> 本轮要决定的视觉问题：填写具体构图、排版或风格问题。
> 逻辑修订、画面 ID 与目标视口：引用当前入口。
> 用户任务、页面状态与固定内容：按必要区域、字段和操作列出。
> 需要保留的品牌、组件与已选方向：引用实际参考，标明不可改变项。
> 容许探索的范围：仅本次已授权部分。
> 不得改变：导航含义、业务状态、权限与操作逻辑。
> 文字不能精确呈现时保留合理占位，准确文本另见文案清单。

没有工具、调用失败或看不到图片时，如实记录依赖该产物的受阻范围，可交出提示词与参考包。提示词、占位链接、HTML 原型和现有代码截图都不是已生成图片。用户明确选定生图方法时，不能偷偷换成原型并宣布完成；其他独立工作可继续，必要时集中确认替代方法。不存在生图要求的 inherit 工作不需要“免生图”批准。

## 4. explore 中选择原型或规格时

真实 HTML/组件原型可以用于选择布局、密度和交互；明确说明它是可运行原型及其模拟边界，实际打开并检查后再引用。具体、可审阅的设计规格也可作为局部决定的依据。它们按自身证据记录，不贴上“图像生成”标签，也不制造生成工具调用。

选择何种方法取决于尚未决定的问题和用户要求。已有充分的设计规格或选定方向时直接细化，只有新的重大视觉取舍才需要确认。原型批准同样不证明真实数据集成或最终实装已通过验证。

## 5. 补足视觉产物的边界

对 inherit 优先引用项目现有定义，对 explore 只补充新形成的规则：

- 精确文案与格式，避免把生成乱码或临时占位带入产品。
- token、组件与状态，标明现有定义、新决定和仍待确认项。
- 支持窗口、滚动、长内容及必要重排；同构状态可由组件规则覆盖。
- 不改变视觉的语义、键盘行为、标签关联和读屏名称；项目明确承诺的标准。

默认以美学与当前方向作视觉取舍。未明确承诺的无障碍比率等只作末位诊断，不因通用阈值重开 G2、改主题或加框/色条/下划线。保留原生行为和合适的既有焦点反馈；不得为了消除报告而隐藏全部反馈。真实内容或操作确实难以辨识时，定位具体问题并作与当前风格一致的最小调整。影响已确定范围或方向的冲突才需要新决定。

## 6. 分工明确的依据顺序

不同产物负责不同事实：

1. 用户最新明确要求和实际授权，决定本次改变哪些旧依据。
2. 当前逻辑与数据契约，决定行为、权限、状态和数据含义。
3. 当前路由所选的视觉依据：inherit 的现有系统与采用中的页面，或 explore 的已选产物和决定；只在各自范围内适用。
4. 精确文案、token、组件、响应式与补充规则，说明画面不能准确表达的细节。
5. 运行代码、截图与测试提供实际实现证据；代码现状或模型猜测不会自动覆盖用户要求，也不会把未批准草图变成决定。

依据矛盾时先核对版本与范围，区分缺陷、新要求和设计取舍。已授权且意图明确的修复直接执行；只有仍未决定、会实质改变范围或方向的问题才暂停相关部分确认。不得用泛化的“旧设计已批准”否定本次要求。

## 7. 实现与实际截图检查

inherit 先复用现有组件和 token，explore 将选定方向落实为共享规则。实现关键屏后尽早查看真实截图，先判断整体美学、构图和视觉一致性，再检查内容、操作、密度、组件状态、长内容和必要键盘路径。需要修正时先找共享原因，不逐页堆叠特殊值。

对比使用可解释的条件：版本、页面/状态、内容样例、角色、窗口、字体、主题与缩放。小改动记录相关条件即可。不同尺寸或不同内容的图片不能假装像素一一对应；新页面可以对照相邻页面与共享规则，不需要虚构一张历史批准图。

每条实质差异注明来源和处理理由，例如本次要求、应修复缺陷、已接受差异或生成噪声。未明确约定数值容差时不制造相似度分数，不把审计脚本通过当作美学通过。实际截图审阅与相关旅程验证始终分开：视觉依据确认不证明播放、提交、保存或权限已有效。

## 8. 接续

恢复当前路由、实际依据、用户要求和未完成事项；旧字段的“G2 待批准/待生成”不是独立的生图指令。先判断它仍代表当前明确要求，还是旧模板的默认项，再据实更新文字说明。保留真实批准历史，mancode 状态和计划变更仍沿其原协议。缺少某项资产或探索图片只阻塞依赖它的部分，不重置已建立的 UI 系统。
