# 按视觉规格开发（v1.2）

目标：围绕完整工作流程和可核对的视觉依据做决定，减少边写边猜与风格漂移。已有系统本身可以提供依据，不要求每次开发都生成新的设计图片。

## 先做什么

1. 先判断是否已有 mancode 管理任务。是：先读 [MANCODE.md](MANCODE.md)，沿原 TaskRef、policy 和绑定模块计划接续，不另建平行任务/验收账本。否：沿普通 Solo 和现有项目入口工作；确需入口时采用 [PROJECT.template.md](PROJECT.template.md)，不因使用本技能自动创建正式任务。先读需求、采用中的页面、代码与测试，区分事实、推断和未知。
2. 读 [SPEC.md](SPEC.md)，确定本次切片、已获授权范围及视觉路由。**inherit**：已有设计系统内接续、添加页面或布局、改交互与局部视觉，先检查 token、组件、相邻页面和真实截图。**explore**：新建视觉体系、整体重做或用户明确探索新方向，才选择生图或原型做视觉决策。单项资产生成不切换路由。
3. 复用依据时核验版本与适用范围；引用图片必须实际查看。采用中的页面可以是事实依据，不等于它曾获得图片审批，也不意味着现有缺陷必须保留。用户最新要求覆盖其明确变更的部分。
4. AI 先整理方案，只把尚未决定、会实质改变范围或方向的问题交给用户。现有授权足以覆盖的局部修改直接推进，不新增选风格、生图或图片批准环节。
5. 涉及布局、组件、动效或 UI 审查时按需读取 [KFL](../kasidia-frontend-law/SKILL.md)，辅助审美判断与实际验证。默认美学优先，无障碍指标为末位诊断；明确的项目承诺仍有效，语义与原生行为保留。KFL 复用本流程的路由、依据与原账本，不另起问卷或自动改造既有风格。

## 关卡与路由

**明确交互逻辑 → G2 视觉依据与变更确认 → 实现真实 UI → 分别验证视觉与行为。**

G2 按 [IMAGE-TO-UI.md](IMAGE-TO-UI.md) 选择证据：

- **inherit**：从现有系统提取本次需要延续的约束，记录变更边界后实现；同体系的新页面、新布局和间距/字号调整不触发强制生图。无重大未决问题且已获授权时，不重复请求图片批准。
- **explore**：按尚未决定的问题选择真实生图、可运行原型或明确的设计规格。需要选择新方向时集中确认影响方向的决定，选定后沿用。只有生图路线要求真实调用图像工具、检查输出并记录来源；原型和运行截图如实标识，不冒充生成图片。
- **asset**：插图、照片、纹理等单项资产按实际需要单独生成，沿当前 UI 的风格与尺寸，不借此重新设计界面。

本包不替换 mancode 的最终执行确认、scope 或重新对齐协议，也不把某种工具的完成当作批准。纯后台、无用户交互或视觉变化时 G2/VIS 可记不适用，仍保留相关范围、数据与行为验收。

视觉依据管外观，交互规格管行为，数据契约管真实数据。对实质冲突只重开受影响决定；已有设计与本次明确要求都不能由模型猜测覆盖。没有明确标准承诺时，不因通用对比度阈值重开视觉决策或机械加框、色条、下划线与文字。

## 交付与接续

恢复工作时先读当前路由、实际依据、本次变更和剩余未决项，不能把旧记录的“G2 待办”直接理解为“必须生图”。按需要迁移其文字说明，不篡改批准历史或 mancode 状态。

每种 UI 路由都须实际查看运行截图，并操作受影响旅程；使用适当的固定样例与目标视口比较。截图不能证明行为正确，模拟数据不能证明真实集成成功。缺少浏览器或检查能力时如实说明受阻范围，不声称验证完成。

交接更新所选模式的当前入口：范围、路由、依据来源与版本、实际授权、未决事项、下一步、已跑及未跑的验证。mancode 状态与 G3 证据走原公共 CLI；不另建通过状态，不自行安装技能或扩大权限。

这些是助手流程约定，不是运行时拦截器；不能声称 mancode 会自动检查图片、审美或强制 G1/G2。
