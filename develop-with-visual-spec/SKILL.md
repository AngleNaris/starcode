# 按视觉规格开发（v1.1）

目标：让用户用完整工作流程和效果图做决定，减少边写边猜、逐个组件返工。流程能暴露遗漏和控制变更，不能保证零返工或自动零漂移。

## 先做什么

1. 先判断是否由 mancode 管理任务。是：先读 [MANCODE.md](MANCODE.md)，沿原 TaskRef、policy 和绑定模块计划接续；该模式优先于下文通用 PROJECT.md 与状态模板，不另建平行任务/验收账本。否：读现有当前事实入口；没有时，经用户授权采用 [PROJECT.template.md](PROJECT.template.md)。先读需求、已有页面、代码与测试，区分事实、推断和未知，不把旧文档或“测试通过”当成完整需求。
2. 读 [SPEC.md](SPEC.md)，确定本次可验收切片和所在关卡。已有批准产物可复用，但必须核验版本、适用范围；复用效果图必须实际查看图片。
3. AI 先整理和提出方案，只将高影响不确定项交给用户，每次合并少量决策；不要求用户填写整份模板。

## 固定阶段顺序

**交互逻辑获批 → 真正生成并批准 UI 效果图 → 实现真实 UI → 分别验证视觉与行为。**

助手不得自行跳过阶段；用户日后明确修改流程时，记录新的约定与适用范围。

此顺序针对相关 UI 切片。纯后台且没有任何用户交互或视觉变化的新任务，无需无关的生图与视觉批准，但仍要明确范围、数据契约与行为验收；不得将有界面影响的任务归为后台来绕过关卡。

- 未获批的切片不进入下一关；不得用代码页面、HTML 截图、线框图或文字描述冒充图像生成结果。原型若另有用途，仍不能代替效果图关卡。
- 图像阶段按 [IMAGE-TO-UI.md](IMAGE-TO-UI.md) 操作。调用环境中真实可用的图像生成工具；没有工具、调用失败或看不到图片时，明确标记阻塞，提供提示词与参考材料包，等待可检查的产物，不声称完成。
- 效果图管视觉，已批准交互规格管行为，数据契约管真实数据。矛盾必须先解决并记录，不能用图片中“看起来像”的状态推导业务规则。
- 新需求先评估影响，只重开受影响的关卡。恢复原有已批准行为或样式的小修复，按 SPEC 的快速路径处理。
- 用同一组数据与视口做截图对比；用真实用户旅程检查跨页面行为、数据持久化和失败路径。截图不能证明行为正确，模拟数据不能证明真实集成成功。

## 交付与接续

每次交接通过所选模式更新当前事实入口（mancode 的任务状态与 G3 证据仍走原公共 CLI）：本次范围、已批准产物引用、实际状态、未决事项、下一步、已跑及未跑的验证。标明模拟／真实数据边界；不把计划测试写成通过。不得自行安装本技能、覆盖项目规则或扩大权限。

这些是助手应遵守的流程约定，不是已安装的运行时拦截器；不能声称 mancode 已自动检查图片或强制 G1/G2。
