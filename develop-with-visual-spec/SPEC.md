# 开发流程规格

此文件可独立作为普通文本规格交给任何能读文件的开发助手。它规定视觉依据、工作边界和验证，不依赖某个技能安装目录或特定工具名称。v1.2 将 G2 定义为“视觉依据与变更确认”。识别到 mancode 管理的任务时先读 [MANCODE.md](MANCODE.md)；其状态归属、模块计划、执行确认与原 policy 优先于本文的通用记录方式。本包不增加 CLI 字段或运行时门禁。

## 1. 工作单位、入口与视觉路由

按“用户能完成的一段工作”切片，例如“选定一个版本，留下意见，再回来查看”，不要按“先做所有按钮、再做所有弹窗”切片。先确认本次目标和授权范围，读实际项目，再判断视觉路由。新增页面不等于新增视觉体系。

| 路由 | 适用情形 | 本次依据与动作 |
|---|---|---|
| inherit：沿用体系 | 继续已有项目、同体系扩展页面/布局/状态、调整交互、间距或字号 | 检查现有 token、组件、采用中的页面、真实截图与明确要求，沿用视觉语言，只改变任务涉及部分；无需重新生图或补办历史图片批准 |
| explore：探索方向 | 新建视觉体系、整体重做、用户明确要求探索新方向 | 针对尚未决定的视觉问题选择真实生图、可运行原型或设计规格；确认必要的方向与变更，再形成实施依据 |

插图、照片、纹理等单项资产生成是独立工作。它沿当前 UI 的风格、位置和尺寸，不会把 inherit 自动改成 explore，也不授权重新设计周围界面。

纯后台、无用户交互或视觉变化时，G2 与 VIS 可记“不适用”并说明理由；仍须明确范围、数据契约和相关行为验收。若发现界面或旅程影响，就补上对应依据与验证，不能借后台名义省略。

通用模式复用一个当前事实入口；确需新入口时可采用 [PROJECT.template.md](PROJECT.template.md)，由 AI 填写。mancode 模式复用 TaskRef 绑定的模块计划（如 docs/media-review.md），不创建第二份 PROJECT.md 状态。入口引用已有文件，无需搬迁；普通 Solo 不因使用本包而创建正式治理任务。

入口应让接手者知道：

- 当前切片、验收条目、授权范围；事实、假设和未决项。
- 当前路由及理由；视觉依据的来源、版本、适用页面/状态和本次变更边界。
- 哪些材料是采用中的实现事实，哪些是用户明确批准的设计；确有批准时记录对应修订与可核对的来源。
- 代码版本、实际完成程度、模拟数据边界、验证结果、阻塞与下一步。

既有系统可作为本次沿用依据，但不能凭“final”文件名、时间戳或正在使用就编造历史批准，也不能把现有 bug、偶然样式和过期页面全部视为设计意图。用户最新明确要求优先于其指定范围内的旧依据；未涉及部分继续沿用。引用图片必须可访问并实际查看，引用代码/组件必须检查实际实现。

## 2. 关卡与放行条件

以下状态只是人工流程表达，不是 mancode JSON 字段或枚举。记录当前依据是否充分、哪些决定待确认、实际授权及阻塞即可；既有批准按真实来源复用。不要为沿用系统制造“历史图片已批准”，也不要因为模板有待填项而重复请求用户已经给出的授权。mancode 的批准与执行条件仍由原 policy 决定；G1/G2 的人工依据在模块附录记录，G3 引用原账本，不另维护独立通过状态。

### G1：交互逻辑

先读可用资料和实际项目，整理本次有变化的部分：

1. 用户、场景、结果与范围外事项。
2. 从入口到完成的主要旅程：操作、系统回应与下一步。
3. 核心实体、关系、权限、状态与持久化；与现有数据/API 的兼容性。
4. 本次需要的页面与正常、空、加载、错误、取消或恢复状态；避免无关状态清单。
5. 可观察的验收条目，以“给定条件 → 操作 → 结果”表达，标明真实可用、受限试用或演示范围。

可从项目确定的事实由 AI 核实；低风险、可逆细节按既有约定处理。只对仍会实质改变成本、权限、核心数据关系、关键路径或验收范围的问题给出建议并集中确认。已明确的需求和已授权的局部修改可以直接使用，不重新发起整套逻辑审批。重大架构选择说明维护、失败和迁移代价，以具体业务情境澄清，不要求用户审数据库细节。

G1 放行：本次逻辑、范围和验收足以执行，所需用户决定已有真实依据，且不存在会推翻本切片的未决问题。受管任务仍须满足原 requirements、计划与执行确认协议。进入 G2 是确认合适的视觉依据，不是自动调用生图。

### G2：视觉依据与变更确认

按 [IMAGE-TO-UI.md](IMAGE-TO-UI.md) 处理所选路由。

**inherit：** 检查项目现有的颜色、排版、密度、布局、导航、组件与交互反馈，优先复用真实 token 和组件；用采用中的页面与运行截图判断意图。为同体系的新页面或布局，说明内容如何进入这套规则、确需新增哪些局部规则。确认本次改动范围与已有依据没有实质冲突后，在现有授权内直接实施。局部间距/字号、同体系新布局以及新增状态，都不单独触发图片生成或图片批准。

**explore：** 只解决真正新的方向问题。根据决策需要选择真实生图、真实原型或足够明确的设计规格；不为了流程完整强制使用某种工具。方向尚未选定时集中展示可比较方案并确认，已有明确选择时沿该选择展开。用户明确要求生图或已选择生图路线时，必须实际调用、查看输出并据实记录；原型、代码截图和提示词不能冒充生成图。工具缺失只阻塞依赖该工具的工作；若需更换已明确选择的方法，说明限制并确认必要的替代决定。

本次视觉依据应覆盖关键页面/状态、目标视口、固定内容样例、精确文案、token、组件和适用布局规则。并非每个状态都要另画一张图，既有组件和布局可覆盖同构状态。真正无法由已有体系推导的方向问题才进入相应探索，不把常规内容排布当成整套风格重选。

默认视觉取舍以美学和本次设计目标为先，兼顾实际辨识与操作。无明确标准承诺时，无障碍数值仅作为末位诊断，不因通用对比度阈值强改配色、重开 G2 或增加外框、装饰色条、下划线与冗余标签。语义元素、原生键盘行为、标签关联和读屏名称等不破坏视觉的实现照常保留；明确约定的无障碍标准仍是本项目要求。真实使用中关键内容不可辨识或动作不清楚时，按具体问题作最小调整，不能用一个数值代替审美判断。

G2 放行：可执行的视觉依据与本次变更边界明确，必要的新方向决定已确认；已有授权内的沿用工作不再增加图片审批。受管任务把这些依据纳入最终计划并沿原协议确认执行。G2 放行不是 VIS 实装验证通过。

### 实现：沿本次有效依据落地

开始前确认框架、组件、资产、数据源和运行环境。保留已有系统及未受影响的界面，不为使用新生成图或参考 kit 无关重写。

- inherit 先复用 token 与组件；explore 将选定方向落实为少量共享规则。先完成关键屏再扩展同类页面，不逐页各造一套样式。
- 精确文案、交互与响应式依据本次规格；图片乱码、遗漏控件和不可能布局不能照抄。依已授权意图可修正的局部缺陷直接修正，实质影响方向或范围时再集中确认。
- 不新增装饰性说明、虚假状态点、无序标题编号、无必要的纯文字操作、失衡空隙或强调色条/下划线来“充实”页面。内容与操作依据用户任务，继承项目已有且有效的视觉表达。
- 开发样例应符合真实实体关系。演示适配层与真实 API 分开；未接通按钮、假成功提示、内存暂存不能冒充实际行为或持久化。
- 新需求或实质设计冲突按变更规则处理，不在实现时默默重做设计系统。

### G3：验收与交付

验收分别报告，不以一种证据代替另一种：

1. VIS（视觉）：实际查看运行截图，对照 inherit 的现有体系和本次变更要求，或 explore 的选定产物。检查构图、层级、排版、密度、组件与真实内容；比较方法和差异可复查。
2. FLOW（交互旅程）：实际操作受影响旅程与必要失败/恢复路径，按相关验收检查前进返回、刷新和状态。
3. DATA（数据与集成）：验证实际适配器、身份/权限、读写与重新读取；使用脱敏或获授权数据。只跑 mock 时只能得出 mock 范围结论。
4. ENG（工程）：运行适用的构建、类型检查与相关测试；这些不能单独证明界面或用户工作已完成。

VIS/FLOW/DATA/ENG 是证据类别，不是 mancode verification surface 枚举。记录环境、代码版本、数据模式、操作/命令、结果和证据；mancode 模式映射至既有验收项与实际观察面，按原 policy 录入同一账本。区分通过、失败、未运行和阻塞，不把预期结果写成证据。

每种 UI 路由都需要实际查看运行截图并操作相关鼠标/键盘路径、展开关闭和焦点恢复；重点检查图标比例/基线、相邻控件、间距、文案与操作状态。沿用体系和已授权局部工作都不免除此检查。截图超时、未查看图片或未完成交互时如实记为未验证，不能宣称 UI 完成；修改后只复验受影响部分。

尺寸矩阵服从目标平台：非移动 GUI 检查实际支持的最小、常用和宽桌面窗口及受影响断点，不机械追加手机/平板或触屏检查。明确的无障碍/DPI/缩放承诺仍保留。保留项目语义、原生行为与合适的既有焦点反馈，不为检查项另加外框、阴影环、内部色条或下划线，也不通过隐藏全部焦点反馈达成外观目标。

只有明确的像素尺寸与容差承诺才采用相应阈值，不能捏造相似度分数，也不能把工具退出成功当作审美通过。G3 放行依实际验收证据与原任务门禁；只证明演示范围时明确交付为演示。交付说明入口、运行方式、完成范围和剩余限制。

## 3. 变更：只处理真正受影响的决定

先明确原因、影响的验收/逻辑/视觉依据/数据/组件和建议。用户已经要求本次修改时不重复询问是否执行；只有尚未决定的重大取舍需要确认。不自动扩项。

- 改用户目标、流程、权限、状态转换或数据含义：更新受影响 G1，评估 G2；若仍在原视觉体系内，继续 inherit。
- 同体系新增页面、布局、组件变体或状态：补齐相应逻辑与视觉规则后沿用，不因“新增”而强制生图。
- 只改间距、字号、颜色等局部视觉：按已授权目标和既有系统直接实现，检查相关页面与共享 token 影响；不自动要求局部生成图或再次图片批准。
- 改视觉体系、整体重做或明确探索新方向：只对相关范围进入 explore，确认必要的方向变化。
- 修复代码偏离有效依据：引用原规则，最小修复并作相关验证。

既有且未受影响的内容继续有效。新要求覆盖其指定部分，旧批准不会覆盖最新要求；现有缺陷也不会因“继承”变成不可改。受管任务若确实改变批准计划，仍须按 [MANCODE.md](MANCODE.md) 走原重新对齐协议；取消强制生图不取消治理批准。

### 小修复与已授权局部工作

恢复有效行为/外观的小修复可引用原验收或设计依据；已有授权内的常规视觉调整也可直接沿 inherit 完成。两者都执行最小实现、相关回归、对应实际截图与证据更新，不新增图片批准。涉及新的范围、数据语义、权限、旅程或视觉方向时，仅重新确认受影响决定。纯后台修复不要求无关截图。

## 4. 权限、阻塞与交接

本流程不授予安装、发布、付款、外发资料、改权限、删除数据或生产迁移的许可。读写、登录和外部工具仍遵循当前用户授权与环境规则。向图像生成服务提交私有剧照、客户素材、人脸或未公开资料前，核对具体资料和目的地授权；无授权时使用合成内容或只准备材料。

接手者读取当前入口、视觉路由及理由、有效依据及版本、本次授权与变更边界、精确文案/token、样例、代码版本和实际证据。继承的是当前可核对的项目事实和有效决定，不能看到旧模板的“G2 待办”就自动生图。旧流程确有未完成的图片要求时，核对它是否仍是用户当前要求；迁移说明不伪造历史批准，也不篡改 mancode 状态。

必要图片打不开时不能凭前任描述复刻该图，必要截图不可检查时不能声称 VIS 完成。缺少图像生成只影响已选择的生图工作，不阻塞依据充分的 inherit；缺少浏览器或测试能力则记录相应未验证范围。继续不依赖缺失能力的已授权工作，不伪造图片、测试或批准。
