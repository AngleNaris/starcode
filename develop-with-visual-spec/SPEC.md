# 开发流程规格

此文件可独立作为普通文本规格交给任何能读文件的开发助手。它规定产物和放行条件，不依赖某个技能安装目录或特定工具名称。配套文件路径相对于本文件。v1.1 增加 mancode 适配：识别到 mancode 时先读 [MANCODE.md](MANCODE.md)；其状态归属、模块计划与原 policy 规则优先于本文的通用入口/记录方式，G1 → G2 → 实现的顺序不变。

## 1. 工作单位与唯一入口

按“用户能完成的一段工作”切片，例如“选定一个版本，留下意见，再回来查看”，不要按“先做所有按钮、再做所有弹窗”切片。先确定本次范围与不做什么；复杂项目可分批批准，不必一次画完所有页面。

图像生成与视觉批准只约束相关 UI 切片。纯后台、无任何用户交互或视觉变化的新任务，可将 G2 与视觉检查记为“不适用”并说明理由；仍须确认范围、数据契约和可观察的行为验收，完成相关实现与验证。若发现影响界面或用户旅程，就补回受影响关卡，不能以后台任务名义绕过。

通用模式只指定一个当前事实入口，默认建议叫 PROJECT.md；采用 [PROJECT.template.md](PROJECT.template.md) 时由 AI 填写。mancode 模式复用 TaskRef 绑定的模块计划（如 docs/media-review.md），不创建第二份 PROJECT.md 状态；已有项目总览可以链接它，但不复制任务/验收状态。入口引用已有需求、设计与测试文件，无需搬迁。用户只处理关键决策。

入口应让接手者在几分钟内知道：
- 当前切片及验收条目；哪些是事实、假设、待决项
- 当前关卡；每个批准产物的稳定标识、文件或链接、修订号、批准人和批准依据
- 每张图片适用的页面、状态、视口和数据样例；可读取的图片文件本身
- 代码所在版本；实际完成程度、模拟数据边界、验证结果、阻塞与下一步

单项目可把逻辑规格、审批记录、变更与测试索引都写在入口中；内容确实变长才拆文件。不要仅凭文件名中的“final”、修改时间或聊天里的“就这样”推定所有版本均获批准。批准必须能对应具体范围与具体修订；产物获批后不可原地悄悄改变，改动需新修订。

## 2. 状态与放行条件

以下关卡状态是人工流程表达，不是可写入 mancode JSON 的新增字段或枚举。通用模式每个关卡记录“未开始／进行中／待批准／已批准／需重开／阻塞”；确无关联的关卡可记“不适用”并说明理由。实现与验证另记“未开始／进行中／通过／失败／未运行／阻塞”。“已批准”来自用户或明确授权的设计决策者，不由实现者自己宣布。mancode 模式的 G1/G2 批准依据写入模块文档的手写附录，G3 仅引用原 verification/review/delivery 账本；不再维护独立“通过”状态。

### G1：交互逻辑

先读可用资料并检查已有项目，再提出一个可审阅方案：
1. 目标用户、场景、这次要完成的结果与范围外事项。
2. 从入口到完成的主要旅程：每步做什么、系统如何回应、下一步在哪里。
3. 核心实体与关系：什么有独立身份、谁能修改、状态如何流转、哪些内容需要持久化。与既有数据和 API 对照，指出不兼容处。
4. 页面与状态清单：正常、空、加载、错误、无权限，以及该任务适用的取消、撤销、部分成功、重试、离线等情况。只纳入真正相关的状态，省略的高风险状态要说明理由。
5. 可观察的验收条目，使用“给定条件 → 操作 → 结果”，为每条赋简短 ID。写清本次是真实可用、受限试用还是仅演示。

先给用户看工作流程和关键取舍，再问会改变成本、权限、核心数据关系、关键路径或验收范围的问题。可推断的低风险细节先列为假设；未确认的高影响假设不得用默认值悄悄放行。一次合并少量关键问题并给出建议，避免问卷式搜集全部细节。

遇到重大架构选择，AI 给出推荐方案和一个合理替代，简述各自的维护、失败与迁移代价。用用户熟悉的业务例子检验一对多关系、版本归属和权限，例如“同一作品的两个版本能否各留一组意见”“谁能改别人已确认的状态”；由 AI 将决定落实为数据契约，不要求用户审数据库细节。

G1 放行：用户明确批准一个修订的逻辑方案、验收范围及接受的假设；不存在会推翻本切片的未决问题。此时可以开始效果图，不能因为流程图完整就开始真实 UI。

### G2：图像生成的 UI 效果图

按 [IMAGE-TO-UI.md](IMAGE-TO-UI.md) 将 G1 转成图像生成任务。先探索一个关键画面的视觉方向，再沿批准方向生成必要页面与关键状态；不要一开始批量生成互不一致的全套页面。

必须使用真实图像生成工具并查看输出的像素。已有已批准图片可以代替重复生成，但要检查图片可访问、版本一致、符合本次逻辑；不因拿到文件名或提示词就视为完成。

交付用户审阅的图像包包含：
- 图片与覆盖清单：哪些页面、关键状态、目标视口已经画出
- 精确文案、组件与设计 token 约定，补足图片无法可靠表达的部分
- 没画出的状态如何沿用已批准组件和布局；响应式、长文本、键盘与无障碍规则
- 图像与 G1 的矛盾或生成缺陷，以及待批准的修订或例外

不要求每个报错都单独生成图片。已有图明确的组件可以覆盖同构状态；新布局、新视觉机制或影响关键操作的状态需要图像依据。不能以“以后开发时再设计”通过 G2。

G2 放行：用户明确批准指定图片修订、覆盖范围与补充规则，关键布局没有未决项。图像生成能力缺失时，本关保持阻塞；准备提示词和参考文件不等于通过。用户另行变更流程时须显式记录，不能由助手自行绕过此要求。

### 实现：按已批准产物落地

涉及 UI 的切片只在 G1、G2 均已放行后实现；纯后台任务按前述“不适用”规则处理。开始前确认框架、已有组件、资产、数据源与运行环境；复用现有能力，避免为复刻效果图无关重写。

- 从图片提取布局、层级、间距、字体、颜色和组件变体，形成少量可复用 token 与组件。先完成关键屏，再扩展同类页面；不要逐页独立手调。
- 精确文案、交互、响应式和无障碍按对应批准规格实现。图中畸形文字、不可读对比度或不可能布局不能照抄；报告差异并确认影响设计的修正。
- 用符合真实实体关系的固定样例开发。演示适配层与真实 API 明确分开，不把原型数据结构默认升级为生产模型。
- 每个关键交互都要有实际行为与反馈。未接通按钮、假成功提示、内存中暂存冒充持久化均须显式标注并计入未完成项。
- 发现新需求或设计冲突时执行变更规则，不在实现中默默重新设计。

### G3：验收与交付

验收分开报告，不以一种证据代替另一种：
1. VIS（视觉）：相同视口、缩放、字体和样例内容下，实装截图对照批准图片；检查整体层级，再检查组件。比较方法、差异和接受理由可复查。
2. FLOW（交互旅程）：按 G1 验收 ID 跑完整旅程，跨页面、前进返回、刷新后状态、恢复和相关失败路径均按约定检查。
3. DATA（数据与集成）：验证真实适配器、身份/权限、读写与重新读取；用脱敏或明确授权数据。若只跑了 mock，只能得出 mock 范围的结论。
4. ENG（工程）：实际运行适用的构建、类型检查、单元与集成测试；这些不能单独证明用户工作已经完成。

VIS/FLOW/DATA/ENG 只用于区分证据类别，不是 mancode 的 verification surface 枚举。每项记录环境、代码版本、数据模式、操作/命令、结果与证据；mancode 模式将其映射至既有验收项与实际观察面，按原 policy 录入同一账本。未运行、失败、阻塞、通过必须区分；“预期通过”不是结果。图片生成的视觉噪声可解释，结构错位、关键操作缺失和可读性问题不能用一句“基本一致”略过。没有预先批准的数值指标时，不捏造相似度分数或百分比承诺。

G3 放行：本次验收条目逐项有证据；阻断缺陷已修复；已接受的限制由用户确认。只证明演示范围时明确交付为演示；真实集成受阻时，不得称整个产品已完成。交付摘要给出入口、运行方式、完成范围、限制与下一步。

## 3. 变更：只重开受影响部分

将新想法先写成一条可判断的变更：原因、影响的验收 ID／逻辑／图片／数据／组件、预计代价与建议。用户尚未决定范围时，由用户决定本次做或放入以后范围；用户已明确要求本次修改时，不再重复询问做不做，只确认仍未决定的方案。不要自动扩项。

- 改用户目标、操作流程、权限、状态转换或数据含义：重开受影响的 G1；检查关联 G2，受影响才重画，再实现与回归。
- 只改视觉方向、布局或组件规则：保留 G1，重开受影响的 G2；修改共享 token 时列出全部受影响页面并回归。纯间距、字号等局部视觉调整，最小交付为受影响关键画面或局部生成效果图、变更规则及一次集中批准；不重做无关页面，也不重新选择整套风格。
- 新增屏幕或具有新布局的关键状态：先补 G1 的覆盖，再生成该部分图片并批准。
- 代码偏离了现有批准规格：可以走下面的修复路径。

已批准且不受影响的内容继续有效。发现规格与代码不一致时，先判断是实现缺陷还是新需求，不自动用代码覆盖规格，也不强迫所有关卡从头开始。

### 小修复快速路径

仅适用于“恢复已批准行为或外观”，例如修复分页丢状态、按钮样式偏离、已批准文案的错字。必须能指向现有验收或设计依据，且不改变范围、数据语义、权限、旅程或视觉方向。

记录问题与依据 → 最小修复 → 运行相关回归 → 有可见变化就检查对应截图 → 更新证据。无需重新询问已经批准的设计或重新生成图片。若诊断中发现必须改变原设计、公共数据结构或用户承诺，立即退出快速路径，按受影响关卡处理。纯后台小修复不要求无关截图。

## 4. 权限、阻塞与交接

本流程不授予安装、发布、付款、外发资料、改权限、删除数据或生产迁移的许可。读写、登录和外部工具仍遵循当前用户授权与环境规则。向图像生成服务提交私有剧照、客户素材、人脸或未公开资料前，核对具体资料和目的地的授权；无授权时使用合成内容或只准备材料。

代码实现者、设计者或另一个助手接手时，必须收到可读取的当前入口、逻辑修订、图片文件/稳定链接、精确文案与 token、验收样例、代码版本、当前状态与阻塞。接手者先核验实际产物；打不开图片就报告阻塞，不能凭前任文字描述复刻。交接记录“做了什么、没做什么、下一个可执行动作”，不只写“继续开发”。

环境缺少图像生成、图片查看、浏览器或测试能力时，记录缺少的具体能力及受阻范围；继续不依赖它的已授权工作，但不伪造截图、测试或批准。解决阻塞后从对应关卡继续。
